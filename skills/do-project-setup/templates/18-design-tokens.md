**Rules — these apply to every screen, with no per-screen variation:**

- **Pick a role, never a value.** Text is styled by assigning a ramp role. A size/weight written directly on a text element is drift, even if it happens to match a role.
- **Emphasis is a weight token only** — bold means `<weight 600>` from the role's emphasis pair. **Never** a size bump, never a different family, never a color change *and* a weight change unless the role says so.
- **Underline is reserved for <inline links only>.** Never for emphasis or headings.
- **Italic: <policy — e.g. not used anywhere in this app>.** <If used: name the exact roles allowed.>
- **Case comes from the role.** No ad-hoc `ALL CAPS` / `Title Case` transforms — if a role is uppercase, it's in the table.
- **No new roles invented per screen.** Need one → ask the user (add vs reuse), then **register it here**.
- **Dynamic type / font scaling:** <how the app responds to OS font-size settings — which roles scale, any cap> — and containers must fit or scroll at the largest setting (widget-spec *Container sizing & overflow*).

## Borders, dividers & hairlines

| Token | Thickness (Android · iOS · Web) | Color role | Used for |
|-------|--------------------------------|-----------|----------|
| `divider.hairline` | <1dp · 0.5pt (1px physical @2x) · 1px> | <`border.divider`> | <between list rows, header ↔ body> |
| `border.input` | <1dp · 1pt · 1px> | <`border.input`> | <text fields, dropdowns> |
| `border.focus` | <2dp · 2pt · 2px> | <`border.focus`> | <focused control> |

**Line rules — this section is where "the line isn't pixel-perfect" comes from:**

- **Thickness is a token, never a literal.** No `1.5`, no computed/scaled thickness. Platform reality differs and must be respected: <Android 1dp hairline · iOS a true hairline is 1 *physical* pixel = 0.5pt @2x · Web 1px, and on DPR > 1 use `<the project's approach>` so it doesn't render blurry or double>.
- **No fractional values** — snap to whole <dp/pt/px>, the declared iOS hairline being the one exception.
- **Inset vs full-bleed is declared, not eyeballed.** <Default: row dividers inset by the screen edge padding; full-bleed only for section breaks.> The inset **is a spacing token**, so the line starts and ends exactly where content does.
- **A divider's length derives from its container** — full width of its parent, never a fixed width/height. A hardcoded length is the "line is shorter on one screen" bug.
- **Vertical dividers:** <thickness · height source (matches content height, or a token) · where they're used at all>.
- **Divider vs spacing:** <when a line is used at all versus just a gap> — don't add a line the standard doesn't call for, and don't replace a specced line with whitespace.
- **One line per boundary.** A card border plus a row divider at the same edge renders as a double-thickness line — pick which one owns the boundary.

## Enforcement

| Check | Platform | Command / mechanism | Gate |
|-------|----------|---------------------|------|
| **No raw literals** — px/dp/sp/pt/rem, hex colors, font weights outside the token file | all | <command — e.g. lint rule / `rg` check wired into the project's lint task> | `do-development` per-stage self-check **+ CI** |
| **Computed style conformance** — font-family/size/weight, border thickness, key region paddings | <web> | <Playwright/Cypress assertions on `getComputedStyle`> | `do-testing` UI level |
| **Screenshot baseline** | <android · ios> | <the tool the repo already has — Paparazzi / Roborazzi / SnapshotTesting; "none" if it has none> | `do-testing` UI level |
| **Tap-target minimum** | all | <a11y check / lint> | `do-testing` UI level |

> **The static no-raw-literals check is the primary gate on every platform** — cheapest, deterministic,
> and it catches the whole class at the source. Computed-style assertions are strongest on **web**;
> **Android/iOS assertion coverage is genuinely weaker** — say so rather than implying parity, and lean
> on the static check plus whatever screenshot-baseline tool the repo *already* has. **Don't add a new
> dependency just for this** (ladder rung 2 — reuse); if the project has no baseline tool, record that as a
> known limitation here instead of pretending the gate exists.
